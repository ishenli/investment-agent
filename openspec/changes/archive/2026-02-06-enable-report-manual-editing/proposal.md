# Proposal: Enable Manual Report Editing

## Summary

Add the ability to manually edit AI-generated weekly reports after they are created. Currently, reports can only be generated by AI. Users need a way to review and modify the report content before finalizing it.

## Motivation

AI-generated reports are helpful but may contain inaccuracies or missing context that users want to correct. Users should be able to:
- Review the AI-generated report
- Edit any section by hand
- Save their changes
- Maintain the markdown formatting

## Why

Currently, when users generate AI-generated weekly reports, they cannot make any corrections or adjustments to the content. This is a limitation because:
- AI-generated content may contain inaccuracies or hallunications
- Users may have specific insights or context they want to add
- The AI may miss important details from the user's notes or market information
- Users should have final control over what is presented in their reports
- Manual editing allows for personalization and customization of reports

Enabling manual report editing provides users with the flexibility to:
1. Correct any factual errors in AI-generated content
2. Add personal insights or context
3. Adjust tone or focus of the report
4. Remove irrelevant or redundant information
5. Ensure the final report accurately reflects their investment journey

## What Changes

This change adds the ability to manually edit AI-generated reports after they are created, which surfaces as:

### 1. UI Changes
- **Report Detail Page**: Add an "Edit Report" button (with Pencil icon) next to the delete button
- **Report Edit Drawer**: A full-height drawer that slides in from the right side containing:
  - Report title and description
  - Full-width textarea for markdown content editing
  - Save and Cancel buttons
  - Unsaved changes detection and confirmation dialog

### 2. API Changes
- **PATCH `/api/report/[id]`**: New endpoint for updating report content
  - Authentication required (user must be logged in)
  - Authorization check (user must own the report)
  - Request validation (content must not be empty)

### 3. Service Layer Changes
- **ReportService.updateReportContent()**: Public method to update report content
  - Permission verification (report belongs to account)
  - Content validation
  - Proper error handling and logging

### 4. Database
- No schema changes required (the `content` field in `analysisReports` table already exists)

## Proposed Solution

The implementation uses a Drawer component that slides in from the right side of the screen when users click the "Edit Report" button:

1. **EditButton**: Added to report detail page, positioned next to Delete button, uses Pencil icon
2. **Drawer Component**: Full-height drawer that provides a focused editing experience
3. **Live Editing**: Textarea that allows markdown editing in full screen mode
4. **API Integration**: PATCH endpoint to persist changes to the database
5. **Safety Features**: Unsaved changes detection and confirmation before closing

Key design decisions:
- Drawer over Dialog: Drawers work better for full-screen editing and are more appropriate for mobile
- No live preview: Simpler implementation focuses on editing experience; users can see final result after saving
- No swipe/ESC close: Prevents accidental closure; requires explicit Save/Cancel action
- Full screen height: Provides maximum editing space for long reports

## Impact Analysis

### Affected Areas

1. **Frontend Components**
   - `src/app/(pages)/report/[id]/report-detail.tsx` - Add edit button and drawer integration
   - New component: `src/app/(pages)/report/[id]/components/EditReportDrawer.tsx` - Report edit drawer

2. **Backend API**
   - `src/app/api/report/[id]/route.ts` - Add PATCH endpoint

3. **Service Layer**
   - `src/server/service/reportService.ts` - Expose and update `updateReportContent` method

4. **Database**
   - `analysisReports` table - No schema changes needed (content field already exists)

### backwards Compatibility

- Existing reports without manual edits remain unchanged
- API endpoints remain backward compatible (new PATCH endpoint is additive)
- No breaking changes to existing functionality

## Alternatives Considered

1. **Inline Editing**: Edit directly on the detail page without a dialog
   - Pro: Simpler UX
   - Con: More complex state management, layout shifts

2. **Version History**: Track all edits with version history
   - Pro: Better audit trail
   - Con: More complex implementation, not requested

Chosen approach uses a dialog because it's a clean separation of concerns and easier to implement reliably.
